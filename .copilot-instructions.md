# adminpsios — Guia para IA / Contribuidores

Documento de referência para futuras inserções (humanas ou por IA) no projeto **adminpsios**.
Leia isto antes de gerar código. Para o módulo NR-1 (DRPS), veja também `docs/MODULO-NR1.md`.

---

## 1. Visão geral

**adminpsios** é o painel administrativo (área interna) do ecossistema PSIOS. É um SPA
**Angular 17** baseado no template **Sakai-ng** (PrimeNG), usando **Supabase** como backend
(PostgreSQL + Auth + RPCs + Edge Functions).

- **Stack:** Angular 17 (módulos NgModule, não standalone), PrimeNG 17, PrimeFlex, chart.js, Supabase JS v2.
- **Backend/DB:** projeto separado em `../../React/supabase-schema` (Prisma schema + scripts SQL + Edge Functions).
- **App público mobile:** `../../React/app-psios` (React/Expo) — não confundir com este.

> O schema Prisma em `supabase-schema/prisma/schema.prisma` é o **espelho** do banco (introspection).
> Não gera migrations automaticamente; as mudanças de banco são scripts SQL aplicados manualmente no
> SQL Editor do Supabase. Sempre atualize o `schema.prisma` **e** crie o `.sql` correspondente.

## 3. Convenções OBRIGATÓRIAS (siga o padrão existente)

### 3.1 Serviços de dados
- Um serviço por entidade em `src/app/demo/service/<entidade>.service.ts`, `@Injectable({ providedIn: 'root' })`.
- Injetam `SupabaseService` e usam `this.supabaseService.client` (`.from(...)`, `.rpc(...)`, `.functions.invoke(...)`).
- Métodos `async`, retornam Promises. Em erro: `if (error) { throw error; }`.
- Supabase pode retornar relacionamentos como **objeto OU array** — normalize sempre
  (veja `mapAplicacao`/`mapColaborador`: `Array.isArray(x) ? x[0] : x`).
- Defina interfaces exportadas para os tipos de domínio; use tipos `*Row` internos para a forma bruta do Supabase.

### 3.2 Telas admin (páginas index)
- Cada tela é um módulo próprio: `<nome>-index.component.ts/html/scss`, `<nome>-index.module.ts`,
  `<nome>-index-routing.module.ts`. Componentes **não** são standalone (`declarations` no módulo).
- Registrar no `pages-routing.module.ts` (com `authGuard`) e no menu (`layout/app.menu.component.ts`, seção "Sistema").
- Importe explicitamente cada módulo PrimeNG usado (Table, Dialog, Dropdown, Chart, Tag, Button, Ripple, Toast, Tooltip, InputText, InputNumber...). `ChartModule` vem de `primeng/chart`.
- Feedback ao usuário via `MessageService` (declare em `providers: [MessageService]` e use `<p-toast>`).
- Padrão de UI: `<p-toolbar>` no topo, `<p-table>` para listas, `<p-dialog>` para forms.

### 3.3 PrimeNG 17 — cuidado com inputs inexistentes
- `p-dropdown` **NÃO** tem input `[loading]` no PrimeNG 17. Para estado de carregamento use `[placeholder]` condicional.
  (Erro real já cometido; não repita.)

### 3.4 Idioma
- Toda a UI, comentários e mensagens em **português (pt-BR)**. Mantenha esse padrão.

## 4. Supabase — padrões de backend

- **Scripts SQL** ficam em `supabase-schema/sql/`. Um arquivo por RPC/migração, com cabeçalho comentado explicando o quê/porquê e instruções de execução.
- **RPCs**: `security definer`, `set search_path = public`, e `grant execute ... to authenticated, service_role` (ou `anon` quando o fluxo é público, ex.: questionário anônimo).
- Ao **mudar a assinatura** de uma função existente: faça `drop function if exists public.fn(<assinatura_antiga>)` antes do novo `grant`, pois o Postgres versiona por assinatura.
- **Migrations idempotentes**: `create table if not exists`, `add column if not exists`, `drop ... if exists`.
  - Ao reconciliar tabela pré-existente, remova **constraint antes do índice** (`drop constraint` remove o índice associado; `drop index` sozinho falha se houver constraint dependente).
- **UPSERT com índice único parcial** (ex.: chave com coluna NULLable): não dá para usar `on conflict` direto — faça `UPDATE ... WHERE col IS NOT DISTINCT FROM $x; IF NOT FOUND THEN INSERT`.
- **Edge Functions** em `supabase-schema/supabase/functions/<nome>/index.ts` (Deno). Secrets via `supabase secrets set`. Nunca colocar API key no cliente Angular; chamar via `functions.invoke(...)`.

## 5. Autenticação e acesso

- Rotas do admin protegidas por `authGuard` (`demo/service/auth.guard.ts`).
- A rota pública `pesquisa/nr1/:token` é **anônima** (sem authGuard, fora do `AppLayoutComponent`).
- Leitura de dados por usuário anônimo pode esbarrar em **RLS**. Padrão adotado: expor o mínimo via
  **RPC `security definer`** validando por token (ex.: `listar_setores_cargos_por_token`), em vez de
  liberar SELECT anônimo nas tabelas.
- **LGPD/anonimato:** o questionário é anônimo por design. Não introduza coleta de PII no fluxo anônimo
  sem necessidade legal. Vínculos temporários (ex.: e-mail para disparo) devem ser apagados ao encerrar
  a aplicação (ver trigger de anonimização no módulo NR-1).

## 6. Build, verificação e ambiente

- Build: `npm run build` (ou `node node_modules/@angular/cli/bin/ng.js build`). Não há testes configurados de forma relevante.
- **Sempre rode o build após mudanças no Angular** e confirme "Browser application bundle generation complete" sem erros de compilação.
- Warnings de **budget** conhecidos e aceitáveis: `pesquisa-nr1.component.scss` (~7 kB) e bundle inicial (~1.01 MB). São avisos, não erros.
- Ambiente Windows/cmd: comandos longos em background podem ser instáveis. Para builds demorados,
  rode via `.bat` + processo em background e leia o log; ou rode `ng build` e aguarde o prompt retornar.

## 7. Regras de ouro para IA

1. **Leia o serviço/tela análogo antes de criar um novo** — copie o padrão, não invente estrutura.
2. Ao mexer no banco: **crie o `.sql` E atualize o `schema.prisma`** (com back-relations nos dois lados).
3. Não adicione dependências npm sem necessidade real (o ambiente de build é sensível). Prefira soluções
   sem lib quando razoável (ex.: QR code via serviço de imagem em vez de pacote).
4. Preserve anonimato/LGPD no fluxo público.
5. Comente em pt-BR, explicando o "porquê" nas partes não óbvias.
6. Após concluir, faça o build e reporte o resultado honestamente (o que foi verificado e o que não foi).
